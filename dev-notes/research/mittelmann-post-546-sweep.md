# Mittelmann NLP sweep after #546 — POUNCE vs IPOPT 3.14.20 + MA57

**Status: measurement record.** This note documents the sweep that closed
[#476](https://github.com/jkitchin/pounce/issues/476) and motivated its
successor [#554](https://github.com/jkitchin/pounce/issues/554). It is a
record of what was measured, not a design proposal.

Data: `benchmarks/mittelmann/ipopt_ma57.json` (the committed reference,
regenerated by this sweep). The POUNCE half lands in
`benchmarks/mittelmann/pounce.json`, which is gitignored by design — POUNCE
results are regenerated per release rather than committed — so the POUNCE
column is reproduced in full in §6 below.

## 1. Why the sweep was rerun

#476 was filed against a tracked MA57 reference that left six instances sitting
at `Maximum_CpuTime_Exceeded`, which made the robustness comparison unreadable
— a timeout and a genuine failure are not the same result.

The reason is worth recording, because the cutoffs look impossibly early
otherwise. The driver passes `max_cpu_time="$TIMELIMIT"`
(`run_nl_bench.sh:253`), and the old reference ran at `TIMELIMIT=300`
(`ipopt_ma57.provenance.json`) — but *unpinned*, so multithreaded BLAS burned
CPU several times faster than wall. `lane_emden120` therefore records
`Maximum_CpuTime_Exceeded` at **89.3 s wall**: 300 s of CPU across ~3.4 threads.
Single-threaded at the same 300 s it would have finished, and in this rerun it
solves in 69.7 s.

The adaptive `theta_max` work in
[#546](https://github.com/jkitchin/pounce/issues/546) /
[#550](https://github.com/jkitchin/pounce/pull/550) also changed POUNCE's
behaviour on exactly the family (`robot_a/b/c`) the issue was filed on, so the
old POUNCE column no longer described the shipped solver.

Both halves were therefore regenerated on one machine, back to back, at a
1800 s limit.

| | |
|---|---|
| POUNCE | `5b336a5c` + #550 (adaptive `theta_max`), `--release` |
| IPOPT | 3.14.20, `~/.local/bin/ipopt-ma57` → `ref/Ipopt/build-ma57/`, `linear_solver=ma57` (confirmed in the log banner) |
| suite | Mittelmann NLP, 47 instances |
| limit | 1800 s wall |
| threads | `OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 VECLIB_MAXIMUM_THREADS=1 RAYON_NUM_THREADS=1` |
| driver | `benchmarks/scripts/run_nl_bench.sh`, mode `pounce` / `ipopt` |
| timing | process wall-clock, measured identically for both solvers (`run_nl_bench.sh:263`) |

Two measurement notes that mattered:

- **The driver hard-codes `IPOPT_LINEAR_SOLVER="${IPOPT_LINEAR_SOLVER:-ma57}"`
  (line 48).** Pointing it at a MUMPS-only IPOPT build produces
  `Unknown_Error` at ~0.04 s on *every* instance, including trivial ones. That
  is what a wrong-linear-solver run looks like; it is not a solver comparison.
- **`solve_time` is process wall-clock for both.** Comparing POUNCE wall-clock
  against IPOPT's internal `Total seconds in IPOPT` excludes IPOPT's startup and
  `.nl` parse and biases the ratio toward IPOPT. All ratios below are
  wall-vs-wall. Independently reproduced with `/usr/bin/time` real.

### 2.1 Relationship to the previously committed reference

`benchmarks/mittelmann/ipopt_ma57.json` is a **committed** reference — it is
regenerated rarely (`make -C benchmarks ipopt-ref-mittelmann`) and every release
thereafter reruns only POUNCE against it. This sweep replaces it, so the change
is worth justifying rather than just landing.

The new run used `~/.local/bin/ipopt-ma57`, a wrapper around
`ref/Ipopt/build-ma57/` — the same build tree that produced the
`ref/Ipopt/install-ma57/bin/ipopt` named in the provenance stamp, so
`ipopt_version` and `linear_solver` are unchanged. What changed is
`timelimit` 300 → 1800 and the addition of thread pinning.

**44 of the 47 timings reproduce within 50%.** The three that moved are exactly
the ones the old run had truncated:

| instance | old | new |
|---|---:|---:|
| `qcqp1500-1c` | 120.1 (cpu-limit) | 1800.1 (cpu-limit) |
| `qcqp1500-1nc` | 119.0 (cpu-limit) | 1800.0 (cpu-limit) |
| `WM_CFy` | 340.6 (cpu-limit) | 1146.6 (solved) |

`robot_a/b/c` land at 170.1 / 166.8 / 165.9 s old vs 170.7 / 176.2 / 164.9 s
new, both at `Maximum_Iterations_Exceeded` — so the failure that #476 was filed
on is reproducible across the two runs, not an artifact of the limit change.

`benchmarks/ipopt_ma57.provenance.json` is a single stamp covering all eleven
suites, and only `mittelmann` was rerun, so it carries a `suite_overrides` entry
rather than being overwritten wholesale.

## 3. Robustness

**POUNCE 47/47. IPOPT + MA57 41/47.**

IPOPT's six non-solves:

| instance | IPOPT outcome |
|---|---|
| `robot_a`, `robot_b`, `robot_c` | `Maximum_Iterations_Exceeded` (3000 it, ~170 s) |
| `qcqp1500-1c`, `qcqp1500-1nc` | `Maximum_CpuTime_Exceeded` (1800 s) |
| `nql180` | `Solver_Error` at iteration 0, 140.4 s |

`robot_a/b/c` hit `Maximum_Iterations_Exceeded` at ~170 s in both the old
tracked reference and this rerun, so that failure is reproducible and not an
artifact of the limit change. POUNCE solves all three to `Optimal` in 190 / 269
/ 222 iterations at 26.5 / 31.8 / 32.0 s — it wins outright against the
reference the issue was filed on.

On `qcqp1500-1nc` IPOPT reaches 2827 iterations before the cap; POUNCE
converges in 77 at 68.5 s.

## 4. Speed on the 41 both-solved

Shifted geometric mean of the ratio, computed as
`sgm(t_pounce, s) / sgm(t_ipopt, s)` with `sgm(t,s) = exp(mean(ln(t+s))) - s`:

| shift | POUNCE / IPOPT |
|---|---|
| 0 s (plain geomean) | 2.07× |
| 1 s | 1.79× |
| 10 s | 1.42× |
| **matched-iteration subset (n=21)** | **2.30×** |

(The per-instance-shifted variant — geomean of `(tP+s)/(tI+s)` — gives 1.71×
and 1.26×. Stated only so the two definitions are not confused; the table above
uses the ratio-of-shifted-means definition throughout.)

### The matched-iteration subset

The overall ratio mixes two effects: per-iteration cost and how many iterations
each solver takes to converge. Restricting to the 21 instances where **both
solvers take an identical iteration count** factors convergence path out, so
what remains is per-iteration cost alone. That subset is **2.30×**, i.e. *worse*
than the overall 2.07× — because several of POUNCE's biggest overall wins come
from taking fewer iterations, not from being faster per iteration.

Worst per-iteration cases, all at matched iteration counts:

| instance | iters (both) | P/I |
|---|---:|---:|
| `steering_12800` | 23 | 8.88× |
| `rocket_12800` | 30 | 8.33× |
| `robot_1600` | 35 | 3.69× |
| `bearing_400` | 16 | 2.98× |
| `pinene_3200` | 13 | 2.90× |

`qssp180` (27 vs 24 it) is 8.78× and `corkscrw` (283 vs 182) is 5.66×. These are
collocation-discretized optimal-control models — large, very sparse, few
iterations, so nearly all the time is in the linear algebra. That is the shape
of the residual gap, and it is what #554 scopes.

`arki0009` is 12.57× overall but 881 vs 353 iterations; its iteration count is a
separate question and is explicitly **out of scope** for #554.

### Where POUNCE wins

The QCQP family runs 3–5× *faster* than IPOPT+MA57:

| instance | P/I |
|---|---:|
| `qcqp750-2nc` | 0.21× |
| `qcqp1000-2c` | 0.25× |
| `qcqp500-3c` | 0.30× |
| `qcqp750-2c` | 0.34× |
| `qcqp500-3nc` | 0.35× |

These are small-`n`, many-constraint problems — the opposite regime from the
collocation models above.

## 5. Corrections to earlier numbers posted on #476

Two claims made earlier in #476 were measured against a **MUMPS** IPOPT and are
wrong against MA57. Both were corrected in-thread:

1. `WM_CFy` was reported as 0.79× "POUNCE faster per iteration". Against MA57
   POUNCE is **1.42× slower per iteration** (2.920 vs 2.062 s/it). POUNCE still
   wins the instance (832 s vs 1147 s) — but on **285 vs 556 iterations**, not
   on per-iteration cost.
2. "The larger half is iteration count on the CFy pair, where per-iteration cost
   is competitive or better" is backwards. `NARX_CFy` is 4.68× total =
   **3.79× per-iteration × 1.24× iteration count**.

The general lesson: on this suite the linear-solver choice moves per-iteration
ratios by enough to flip a conclusion's sign. A MUMPS reference cannot be used
to make a per-iteration claim about MA57.
